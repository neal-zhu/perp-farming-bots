# Perp Farming Bots：独立自托管设计

日期：2026-10-12（Asia/Shanghai）。状态：主体已转为真实账户与订单接入；本文件包含后续设计，已实现范围和验证状态以 README.md、STATUS.md 为准。

## 1. 目标与实现原则

为用户提供一个在自己的设备或服务器运行、内置多种策略的 perp farming bots 应用。用户不需要写代码、编辑策略文件或配置数据库；通过策略卡片创建多个 bot，每个 bot 使用独立参数和可核对的成交分配。对冲是第一版策略，后续支持网格和剥头皮等永续交易策略。下文涉及两腿的规则仅归属于对冲策略，不限制共享运行模块的订单数量和持仓形态。

本项目完全独立。禁止从私人项目复制、导入、移植代码、测试、配置、fixture、数据库或内部设计文档。不将私人仓库作为依赖、子模块、生成输入或恢复资料。只依赖公开库、官方资料和本项目自行编写的规格。

最快交付的选择是复用公开 SDK 和 UI 框架，自行实现范围有限、持久化的策略运行、执行操作与成交分配。首个执行路径是双腿对冲；共享模块不把所有订单包装成两腿，也不预先建立复杂的策略 DSL。不会假设 SDK 已经提供跨场馆原子成交、重复请求保护或重启后的操作恢复。

用户补充：主体开发优先，不投入极致性能或过多可靠性优化。先使用单进程、简单表结构和普通事务交付；真实执行的必要订单身份与未知状态约束仍保留。Bot 绑定具体账户实例，同一交易所可以有多个账户；两个不同的 Arcus 账户也可以构成对冲策略，不能因 venue 相同而拒绝。相同原生账户的多把 API key 不能伪装成账户隔离。

### 产品层次和策略接口

产品层次为：策略库 -> bot 实例 -> 执行操作 -> 订单/成交/持仓。bot 实例是用户的主要操作对象，一个 bot 可以在其生命周期内产生多个订单、成交和策略轮次。

| 名词 | 所有权和含义 |
| --- | --- |
| Strategy definition | 内置策略类型、版本、参数 schema、说明、需要的场馆能力 |
| Bot instance | 用户选定策略及参数、账户绑定、运行状态、预算、策略状态版本 |
| Execution operation | 一次已授权动作，可有一条腿或多条腿；负责提交、确认、取消及恢复 |
| Allocated inventory | 根据成交事实归属到 bot/策略轮次的数量，独立于交易所账户净仓观察 |
| Strategy state | 网格层级、待处理成交、轮次、对冲等待条件等，由对应策略模块维护 |

共享模块负责账户接入、行情、能力声明、资金/订单预留、幂等、提交前持久化、查单、成交分配、盈亏、积分和通知。策略模块负责何时入场、出场、挂单、撤单、补单及如何解释自己的状态。策略只产生带 bot_id、原因、数量/价格约束和动作类型的明确请求，不直接调用 SDK 下单。

首版仅实现对冲模块。接口以对冲真实需求为起点，同时用一个单腿生命周期契约测试确认共享执行不依赖固定 LegA/LegB；新增网格时再根据真实差异完善接口，不建设通用指标引擎、脚本编辑器、可视化策略编排或自由加载远端代码。

网格首先需要确定方向、库存预算、价格区间、层级数量、区间外行为和暂停/平仓行为。剥头皮首先需要确定可验证的入场/出场条件、订单类型、单笔和累计预算、冷却与结束条件。网格的当前已实现规则见 GRID.md；剥头皮仍仅为策略类别。

## 2. 技术栈与发行形态

| 部分 | 选择 | 原因 |
| --- | --- | --- |
| 运行时 | Python 3.12 / asyncio | 与官方 Lighter SDK 同语言；适合网络 IO 和快速开发 |
| 页面 | NiceGUI | 复用表单、卡片、表格、对话框与图表；无需额外 Node 构建流程 |
| 接口 | NiceGUI 所基于的 FastAPI | 同进程提供操作与查询；避免维护独立前后端部署 |
| 校验 | Pydantic | 严格请求校验和显式状态模型 |
| 数量和金额 | Decimal；原生整数 tick/step | 禁止二进制浮点参与订单数量和账本累加 |
| 持久化 | SQLAlchemy / Alembic / SQLite | 单用户实例、事务、迁移、备份，不要求安装数据库服务 |
| 官方接入 | elliottech/lighter-python | 已在公开源码中验证 Robinhood 签名域 |
| 广泛接入 | CCXT / CCXT Pro | 复用已验收场馆的 REST/WS、市场元数据、精度和订单接口 |
| Arcus 永续 | 本项目独立 adapter | 公开组织仓库中未找到永续下单 SDK；spot SDK 不可代用 |
| 通知 | HTTP 客户端调用 Telegram Bot API | 单向告警；站内通知始终保留，不引入额外队列服务 |
| 测试 | pytest / pytest-asyncio；UI 浏览器验收 | 聚焦订单不确定、崩溃恢复、分配与独立关闭 |
| 发布 | Docker Compose / 单个应用镜像 | 用户只启动应用，挂载 data 和本地密钥目录 |

NiceGUI 是服务端驱动 UI，并且采用单 worker。第一版明确只启动一个执行实例，关闭热重载。后台任务在应用生命周期中启动，由持久化操作驱动，不依附页面 timer、浏览器连接或单个请求。

同步或原生 SDK 操作不得阻塞行情事件循环；必要时用受控工作线程，同时按账户/签名资源串行化。实现前测试原生 signer 的线程与客户端隔离，不假定线程池自动使 SDK 安全。

不引入 Redis、Celery、PostgreSQL、Kubernetes、多租户云控制面或策略市场。也不建立可配置的通用策略语言。

## 3. 为什么不整体 fork 成熟交易机器人

Hummingbot、NautilusTrader、Freqtrade 是调研对象，事实和版本证据见 research/frameworks.md。选择依据是本产品的具体接入和部署成本，而不是是否有套利策略示例。

Hummingbot 的现有连接、V2 执行能力和 Dashboard 值得参考，但完整 API/UI 路线引入更多部署部件，公开 Lighter connector 的域支持不能自动等同于 Robinhood。Arcus 还需要独立接入。

NautilusTrader 当前源码已经包含 Robinhood 相关支持，因此不能说它不支持。仍需区别源码版本与已发行软件版本，以及 Rust 接入与 Python 可调用的范围。对于这个简单自托管工具，完整交易框架集成、发布和许可证处理未必比 SDK 路线更快。

CCXT 本身是连接库，不是本产品的双腿恢复引擎。使用其 MIT 代码及免费开源的 Pro WS 能力，不把核心场馆的端点覆盖当作已验证的新部署接入。

公开例子可以帮助理解接口。仅在实际需要复制代码时登记具体路径、上游版本、许可证与 notices；不将某个示例脚本默认视为生产交易协调器。

## 4. 用户流程

### 初次使用

1. 安装发行包并启动实例；首版提供 Docker Desktop 和 Linux/VPS 的图文说明。
2. 打开本地浏览器。当前本地开发版本免登录，最终安全方案待定。
3. 选择场馆和部署，填写 API 凭据；页面帮助解析原生账户索引等可查询字段。
4. 执行只读账户验证，展示权限、余额、已存在仓位、订单与限制。
5. 配置并测试通知。测试消息需要用户点击；未启用通知也可查看站内状态。

程序不要求主钱包助记词或主钱包私钥。新平台若不能提供适合本产品的受限 API 授权，不能为了接入而默默改用主钱包密钥。

当前默认绑定本机回环地址。安全和登录设计留待主体开发后确定，包括远程访问和 UI、HTTP、实时连接的访问控制；不预设采用密码或 Basic Auth。

### 创建

产品首页使用 bot 列表和“创建 bot”，先选择策略，再显示该策略的表单。对冲表单如下；未来网格和剥头皮显示各自字段，不要求用户填写无意义的第二交易所或价差阈值。bot 详情分别展示运行状态、订单、库存、成交、成本和异常；策略专属视图展示双腿进度、网格层级或剥头皮轮次。

对冲策略表单只有：两个场馆账户、币种、价差条件、目标金额。方向由当前行情预选，提交前以文字展示两边多空，用户确认后固定。不要在等待时悄悄反转方向。

金额为单侧目标敞口，不是总保证金或两腿交易额之和。后台换算为相同经济基础数量，另一腿的报价金额可能不同。两腿数量、保证金估算、开仓费用估算、当前价差和滑点限制在确认卡中显示。

V1 只支持已经验证的线性永续与匹配的基础资产单位。反向合约、复杂 RWA、不同指数定义和重基代币需要独立单位验证；ticker 相同或价格接近不能证明是同一资产。

价差使用所需数量对应的买入/卖出 VWAP，不能使用 last price。页面预览、条件判断和下单前检查使用同一单位和同一公式。对于单位比例为一的开仓：

`spread_pct = (short_sell_vwap / long_buy_vwap - 1) * 100`

阈值是成交价差条件，不代表已扣费用的净利润。费用和预计资金费单独展示。提交前用已知新鲜行情复核，但不能承诺跨平台原子成交或最终两腿价差绝对等于预览。

### 查看和关闭

bot 运行状态与订单/操作状态分别展示。交易操作只有运行、暂停、平仓。运行也用于恢复暂停的策略；暂停禁止新的策略动作并保留持仓，已提交订单仍需核实。平仓提交独立的减仓操作，仅关闭最后确认的 Bot 分配数量。未确认订单和不匹配持仓保持显式的“需要处理”，不得靠运行绕过。取消挂单属于具体策略的订单处理，不增设独立的停止按钮。

V1 对冲已完成建仓后主要供用户主动关闭；后续网格和剥头皮的出场/补单规则按用户选定的策略自动执行。每个 bot 都可独立操作，暂停或平仓一个 bot 不调用账户级全部撤单或全部平仓。

首页直接展示当前仓位、等待建仓和需要处理的操作。每个仓位有自己的 ID、方向、实际数量、目标完成度、费用、资金费、盈亏、历史和关闭按钮。

关闭页面明确关闭哪些分配数量和允许的滑点。一次点击提交持久化关闭操作，返回进度；重复点击返回同一操作。断开网页不取消操作。

程序停止时行情监测停止，但交易所仓位保留。页面和安装说明必须解释这件事。自托管减少远端平台依赖，不消除常驻设备需求。

## 5. 多仓位模型：从第一天区分策略持仓与交易所净仓

每个 bot 的库存由其成交分配得到，可以拥有一个或多个策略轮次/lot。对冲策略的一个 lot 包含两腿；网格或剥头皮不必须拥有两腿。交易所原生持仓可能将多个 bot/lot 的同向合约库存合并为一个净仓。

这两者是不同含义，不是两个可互相兜底的数量真相。应用 lot 的数量只能从唯一成交事实及其分配投影得到；原生仓位快照是外部观察，不能用作猜测 lot 数量的后备字段。

第一版支持：

- BTC、ETH 等多个币种同时持仓。
- 任意经过验收的不同交易所组合。
- 相同 pair、相同方向，重复创建多个独立 lot。
- 同一原生账户同一合约的同方向腿，由多个 lot 共用并合计。
- 每次关闭只减少选中 lot 的精确分配数量，其他 lot 不被整仓关闭。

第一版禁止同一原生账户同一合约上的相反方向 lot。单向净仓模式会相互抵消；不能让两张 UI 卡片制造两边都存在的错觉。需要相反方向的用户使用不同原生账户/子账户；账户身份必须明确隔离，不通过改显示名称实现。

示例：lot A 为 Arcus BTC 多 0.01 / Lighter RH BTC 空 0.01，lot B 为 Arcus BTC 多 0.02 / Lighter RH BTC 空 0.02。原生两边各有 0.03。关闭 A 只下单减少各 0.01，B 保留各 0.02。

订单填写本次精确数量，不调用 SDK 的 close-all/flatten-all。每笔 fill 先写唯一事实，再在同一事务中分配给其操作及 lot。数据库约束保证 fill 不重复入账、分配不超过真实成交。未分配事实保持明确未分配。

账户-部署-原生合约键下的开仓、关闭、补偿、观察修复串行；操作需要两个键时按统一排序获取，避免死锁。账户资金有独立预留，避免多个合约把同一可用保证金重复预算。暂停或不确定状态只影响相关账户/合约和共享资金资源，不冻结不相关场馆。

V1 推荐使用专用交易账户。账户内既有仓位不自动导入为产品 lot。在平台手动交易、强平或 ADL 导致数量变化时，用可核实的成交事件记录变化；无法归属的变化显示需要核对，阻止该合约新的自动提交，不把差额随意摊给所有 lot。用户能进入带证据与预览的处理流程。不存在“用最新快照覆盖全部 lot”的恢复捷径。

新策略不能自动继承对冲策略已验证的同向共享方式。网格和剥头皮首个版本默认独占原生账户/合约，除非其挂单、迟到成交、取消竞争及库存分配均已通过跨策略共享验收。普通 reduce-only 卖出已有多仓库存不等于新开空仓；必须按操作意图和分配数量区分。未验收的交叉策略组合在创建前明确提示改用其他账户/合约，不能隐式净额合并。

## 6. 持久化执行，而不是浏览器按钮直接下单

bot 控制模块提供参数预览、创建、运行、暂停、平仓和详情。运行兼用于恢复，暂停可取消等待建仓。共享执行模块处理提交、取消、明确的改单、关闭分配库存及操作查询；一条腿/多条腿用明确操作类型和恢复规则表达，不能填假第二腿。页面和 HTTP 入口调用同一模块。操作 ID、bot_id、幂等键、参数哈希和状态版本持久化。相同幂等键不同参数返回冲突。

对冲策略的基础执行流程：

1. 校验市场身份、账户域、两腿单位、数量网格、余额、行情年龄与授权范围。
2. 事务写入操作、资金预留和第一次订单提交身份。
3. 按确定账户域准备/签名；落盘原生 nonce、client index、签名身份和有效期等恢复所需信息。
4. 提交第一腿受价格保护的 IOC。
5. 核实原订单终态与实际成交，按成交经济数量计算第二腿。
6. 持久化第二腿提交记录，然后提交受保护订单。
7. 入账真实成交和费用。已成交但费用未知时允许成交状态完成，同时盈亏标记费用未确认。
8. 已知异常失败按事先授权的规则补偿本次新增数量；未知订单先查询，不能盲目补偿或重发。

默认走先确认成交、再按实际数量对冲的顺序路径。前后两腿之间仍有价格风险；第一版不声称两腿原子。并行提交可以作为后续经过验证的优化。

如果部分成交产生第二腿不可执行的数量，不能把请求量伪装为成交量。优先按真实第一腿数量做本次操作补偿；无法完成时保留剩余敞口和需要处理状态。实际建立金额可低于目标，展示部分建仓，用户明确选择继续或关闭；不自动重复建仓刷量。

正常关闭使用每个 lot 的剩余两腿数量以及 reduce-only 原生语义。低于最小单的残量只有在原生关闭豁免得到验证时才能直接处理。V1 不通过未授权的扩大仓位或反向超量单解决尾仓；不能处理时保持未关闭并告警。

### 原订单恢复

下单 HTTP 成功只证明收到相应响应，不自动证明成交。超时、查无记录、历史接口不可用、连接中断与已确认零成交是不同状态。

程序在准备、提交前、提交后响应丢失、成交入账前、成交入账后、第二腿提交前各崩溃点都可恢复。启动先扫描未完成操作和提交记录，依据原生 client ID / nonce / tx identity 查原订单。没有确定证据时保留未知并禁止相关替代提交。

SDK 高层签名并发送函数不能绕过提交前持久化。Lighter 公开源码提供独立 sign_create_order 与 send_tx；实现时使用这类分离接口并验证每个返回值，不直接使用一个不可观测的 fire-and-forget 调用。

单实例持有本机数据目录独占锁。SQLite 事务不能防止不同机器使用复制的数据库和同一密钥并行交易；恢复安装必须先停旧实例，不能把复制 data 目录宣传为双活部署。

## 7. 无主动风险管理的精确定义

共享运行模块不自行执行止损、止盈、重新对冲、保证金补充、调杠杆或 ADL 后对侧减仓。首版对冲策略不包含这些主动风险行为，也不包含重复 round-trip。未来网格的挂单/补单和剥头皮的规则出场是用户选定策略本身的交易规则，必须在创建页面明确说明；不把“无主动风控”解释成所有策略都禁止正常出场。

用户发起建仓前的不可执行拒绝、建仓异常的操作内补偿、用户明确发起的关闭以及原订单恢复仍需要运行。这是执行用户操作的规则，不根据持仓收益或风险重新替用户做交易决定。创建前说明失败时如何补偿及金额约束。

强平/ADL 观察和事件入账不自动触发对侧交易。未核实的风险数据不会展示成零风险。告警只陈述平台数据、观察时间、缺失字段和用户可采取的操作。

## 8. 盈亏、费用、资金费与积分

盈亏来自应用实际成交和分配，不来自账户余额涨跌。账户充值、提现与外部交易不能计为本程序收益。

`net_pnl = realized_price_pnl + unrealized_price_pnl + settled_funding_received - settled_funding_paid - confirmed_fees - confirmed_other_costs`

金额以 Decimal 文本或有明确 scale 的整数存储；不用 SQLite 的浮点 NUMERIC 转换作为金额真相。展示币种换算需要明确价格来源和时间；USD、USDG、USDC 不默认视为完全相等。无法转换就展示原币种并标记不能汇总。

开仓与平仓 fill 的费用可以精确分配到所属 lot。平台提供账户/合约级 funding 时，根据已核实的结算规则分配；若只能按某时点数量或时间权重估计，必须标为分摊估计，不能称为平台对该 lot 的官方结算。已确认账户总额、分摊方式和舍入余量应可核对。发布规则缺失时只展示可核实账户级 funding，不猜 lot 数据。

积分单独运行低频读取任务，按场馆、原生账户、项目和赛季展示。不同项目不能合计；账户积分不能直接归属某个 lot。官方暂未公开、未结算、读取失败、上次数值过期、接口未接入和资格未确认分别建模。

已找到的 Lighter SDK referral_points 不能被命名猜测为所有用户交易积分接口。Arcus 的 spot SDK 也不能被当作永续积分接口。读取路径和项目规则要单独验证。

Arcus 官方 Annex C §8(c) 对主要用于积分 farming 的对冲或 delta-neutral 活动规定积分资格限制。因此 Arcus 可作为执行试点，但产品不能承诺其对冲 lot 计入积分。原生积分仅作平台事实展示；未获确认时不预测积分或空投美元价值。

## 10. 试点与全部场馆的扩展

将旧产品需求中的“支持已有交易所”重新定义为一个公开、独立维护的场馆支持表。任何私人 adapter 的存在不能成为此项目已支持的证据。

| 场馆 | 开发路线 | 当前已核实 | 发布前工作 |
| --- | --- | --- | --- |
| Lighter RH | 官方 Python SDK | 公开源码有 RH 域和 466324 签名 ID | 账户/市场单位、nonce、fill history、重启恢复和小额交易验收 |
| Lighter Core | 同一 SDK，不同独立部署配置 | 官方 README 和 SDK | 分别验证账户、目录、抵押币与限制；不共用凭据 |
| Arcus 永续 | 独立 HTTP/WS/签名 adapter | 官方组织有 spot SDK 和 DA reader；未找到永续下单 SDK | 获得可访问官方协议资料，独立实现认证、下单、查单和成交恢复 |
| 其他线性永续 | CCXT/Pro 已验收实例 | 统一库与场馆目录 | 逐项认证、订单身份、reduce-only、费用、资金费与恢复验证 |

如果最快可用 beta 优先于固定 Arcus 试点，可以先做 Lighter RH 与一个公开库已支持且验证通过的对侧场馆；Arcus 在同一接口后补齐。若要求第一个真实 pair 必须是 Arcus ↔ RH，Arcus 的独立 adapter 和官方协议访问就是关键路径，不能用只读页面掩盖它。

支持表区分：未接入、公开行情、账户只读、交易验证通过、暂时故障。库的 symbols 列表不等于完整生产支持。发布后每个 adapter 固定上游版本，升级需重新通过受影响契约。

## 11. 告警和可观测性

站内通知与 Telegram 为 V1 渠道。内容包括实际完成、单腿异常、原订单未知、关闭剩余、账户授权失效、行情不可用、程序恢复、平台强平/ADL 和积分同步问题。

告警应带 lot/操作链接、平台名、实际已知状态、时间和可执行下一步。投递失败不阻塞下单确认、关闭或账本写入；保留失败状态并去重重试，避免消息轰炸。

健康接口区分进程活着、执行循环活着、数据库可写、场馆可读和是否仍有未知提交。行情缺失不能被首页绿色总状态掩盖。完整主机离线无法由该主机自身发消息；可提供可选的外部心跳监控集成，默认不要求远端托管账户或遥测。

## 12. 自托管发布与许可证

首版发行一个非 root 应用容器，挂载本地 data 和密钥目录。镜像只读部分与可写数据分离，设合理停止超时和 restart policy。Docker 自动重启不能证明交易状态安全，必须先恢复未完成提交。

凭据在本地加密保存，主密钥来自本机文件/secret mount；明示其防护范围是离线数据泄漏，无法抵御已经控制主机的攻击者。用户有加密备份导出，包含交易数据库和密钥恢复所需材料；普通诊断导出不含签名 payload 或凭据。

先验证 Linux amd64 / arm64 的官方 signer 导入与签名准备，再承诺对应容器架构。macOS / Windows 用户可经 Docker Desktop 使用；桌面安装包为后续发行工作，不把它算入首版现成能力。

本项目采用 Apache-2.0。所有实际依赖固定版本与哈希，生成实际依赖清单和许可证 notices。不要自动添加 builder、integrator 或 referral 标识；默认不收取隐含费用。SDK/库若默认启用此类参数，显式关闭或在无法确认时拒绝启用相关实盘路径。

## 13. 交付顺序与时间假设

优先完成对冲策略读写闭环，再扩大场馆数；随后补充网格和剥头皮策略。详细任务见 IMPLEMENTATION.md。下列估算只覆盖首个对冲策略，不包含未定义的其他策略实现。

粗略估算以一位熟悉 Python 异步和交易接口的开发者全职实施为前提，不是交付承诺：可点击只读版本约 2–4 个工作日；已有 SDK 场馆的两腿执行与原订单查询流程约再 5–8 日；小额实盘与多 lot 独立关闭验证约再 5–8 日；Arcus 独立接入可能另外需要 5–10 日或更多，取决于官方协议和恢复接口可用性。

2–4 周可作为已有 SDK 场馆 beta 的目标；包含 Arcus、多个场馆和安装发行的稳定试点按 4–6 周评估。界面、真实行情、真实账户、真实下单和完整双腿恢复分别验收，不能合并宣传成“已完成”。

## 14. 必须通过的验收

- 相同请求双击、重试和重启后不会创建第二次交易操作。
- 每个关键提交/成交落盘点崩溃后，查原订单而不是下替代单。
- 第一腿部分成交、第二腿异常、两腿结果未知都保留正确事实。
- 多个同向 lot 共用原生净仓，独立关闭不减少其他 lot 的数量。
- 多个 bot 独立运行、暂停与平仓，状态和订单恢复不互相串用。
- 网格/剥头皮策略后续需要分别通过挂撤单竞争、迟到成交、库存预算及重启状态验收。
- 同一账户反向 lot 在发送前明确拒绝；不同原生账户可隔离。
- 本程序外部交易与 ADL 事件不能被当成某 lot 的普通成交。
- DB 写失败、磁盘满和 SDK 查询失败不会被转为成功或零成交。
- 行情过期/断流、精度/最小量缺失、保证金不足在提交前明确处理。
- 费用、资金费、积分缺失有可见状态，盈亏不编造零值。
- Telegram/图表/积分读取异常不拖住订单确认与关闭。
- 浏览器关闭、页面重连、程序重启不丢失已接受的操作。
- 禁止隐含 referral/builder 费用和未经请求的风险交易。
