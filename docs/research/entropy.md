# Entropy native integration

Verified 2026-10-14 from primary sources; no private repository artifacts used.

- [Official Entropy](https://entropy.io) and its [public market catalog](https://entropy.io/api/markets?scope=all): BTC, ETH and SOL are Hyperliquid default-DEX markets, native asset IDs 0, 1 and 5. Entropy `io:*` instruments are distinct HIP-3 contracts. The adapter reads all active main and `io` markets; qualified names are retained.
- Official frontend `assets/builder-D2NcoSIw.js`: builder `0xcD254d2A328f7f67C7c6FEf930A4757516F7b601`, added builder fee `0`. This is explicit configuration; it does not authorize future fee increases. The frontend configuration uses mainnet `https://api.hyperliquid.xyz`. No frontend code was copied.
- [Official Python SDK](https://github.com/hyperliquid-dex/hyperliquid-python-sdk), pinned PyPI release **0.24.0**, [MIT license](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/LICENSE.md). Only its EIP-712 `sign_l1_action` is imported. The application independently prepares exact Decimal wire values and passes them through its existing encrypted journal and single-send transport.
- [Official API info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint) and [perpetual info requests](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals): `userRole`, SDK-documented `extraAgents`, `approvedBuilders`, `userAbstraction`, `clearinghouseState`, `activeAssetData`, `meta`, `l2Book`, `metaAndAssetCtxs`, `fundingHistory`, `orderStatus` and `userFillsByTime` are read-only POST `/info` requests. This exact endpoint can retry; POST `/exchange` cannot.
- [Tick and lot rules](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/tick-and-lot-size): size uses `szDecimals`; fractional perpetual prices use up to five significant figures and at most `6 - szDecimals` decimal places; integer prices are valid. Native minimum trade notional is 10 USDC, with reduce-only exceptions handled by the shared executor.
- [Exchange endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint): a 128-bit hexadecimal client order ID identifies the original IOC order, including after a lost acknowledgement. Mainnet actions use monotonically increasing millisecond nonces and a 30-second expiry; signing happens before journaling, journaling before sending.
- [Builder codes](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/builder-codes): existing main-wallet approval is checked, never created. Orders carry the official Entropy builder with zero added fee. This is order attribution, not a guarantee of farming eligibility or points.
- [Fill schema](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions): the monetary `fee` already includes `builderFee`; never add it twice. USDC fees can be accounted, including rebates; another fee token remains unknown.

## Account and recovery scope

The supplied address must be the main trading account. The supplied private key must be an approved, unexpired API agent belonging to that account; main-wallet keys are rejected. No subaccount or vault inference is performed. Standard accounts read the selected DEX’s collateral. DEX-abstraction uses the main USDC perpetual collateral source for io trades, following the native protocol’s existing abstraction setting; unified/portfolio margin is rejected explicitly until its balance and collateral semantics are implemented.

Margin leverage/mode is read through `activeAssetData`, including flat markets. Setting it uses the shared journaled margin workflow and native read-back confirmation. Position margin is explicitly unknown when this response does not supply it; no guessed zero is presented.

[Asset ID rules](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/asset-ids) define HIP-3 IDs as `100000 + perp_dex_index * 10000 + index_in_meta`. The `io` DEX index is discovered through `perpDexs`, never hardcoded. Metadata, asset contexts, clearinghouse state and open orders use their DEX scope; books, funding history, active-asset data and fills use the fully qualified coin name. Main and io catalogs currently use collateral token 0 (USDC).

[Account abstraction modes](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/account-abstraction-modes) and the [native DEX abstraction action description](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint) establish the collateral source. The adapter reads this mode without enabling abstraction or submitting transfers. Isolated-only rules and leverage limits come from each market’s own metadata.

Only native terminal orders with matching client ID, market, side, original quantity, limit price and reduce-only flag may be applied. Fills match native order ID and unique trade IDs. A missing order, incomplete fill count, truncated history or malformed identity remains unknown and cannot enable another leg. An explicit native rejection is evidence; a missing acknowledgement is not. No unconfirmed order is resent.

Public mainnet catalogs, books and funding are validated separately from funded-order acceptance. Automated tests cover native schema/precision, agent ownership/expiry, approved builder, signed IOC payloads, original-client-ID recovery, partial cancels, missing fills, monetary fees, native leverage and POST-read versus POST-write retry behavior. Funded-order acceptance is still an operator verification step; no funded order was submitted during implementation.
